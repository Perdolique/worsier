# Worsier

Worsier is a focused JavaScript, TypeScript, JSX, TSX, and Vue SFC script formatter powered by Rust. Each rule is independently configurable, and source outside enabled rules is preserved instead of being reprinted.

Node.js 24.0.0 or newer is required.

## Installation

```sh
pnpm add -D worsier
```

Check a project without changing files:

```sh
pnpm exec worsier --check .
```

Format it in place:

```sh
pnpm exec worsier --write .
```

## CLI

| Command | Purpose |
| --- | --- |
| `worsier file.ts` | Format one file and print the result |
| `worsier --check PATH...` | Check files or directories without writing |
| `worsier --write PATH...` | Format files or directories in place |
| `worsier --stdin-filepath file.ts` | Format stdin using the supplied file type |
| `worsier --config path/to/worsier.jsonc` | Use one explicit configuration |
| `worsier --init` | Create a complete `worsier.jsonc` |
| `worsier --threads 4` | Set the number of formatting workers |
| `worsier --no-verify` | Disable AST verification for one invocation |

Directories and multiple files require either `--check` or `--write`. Directory discovery skips `.git`, `node_modules`, and Wrangler's generated `worker-configuration.d.ts`. An explicitly passed file is still processed even when it matches an ignore rule.

File and stdin output preserve whether the source ends with a newline, including when using the npm CLI.

Supported files are `.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts`, `.tsx`, and `.vue`.

`--write` opens each source without following a leaf symbolic link and overwrites changed files directly through the verified file handle, so the file itself must be writable; multiple input paths that identify the same file are rejected, an interrupted write can leave a partial file, and successful exit does not force data to persistent storage.

## Configuration

A configuration file is optional. For every input, the CLI searches upward for the nearest `worsier.jsonc`, stopping at the Git or filesystem root. An invalid discovered or explicit file is an error; Worsier does not silently fall back to defaults.

This is the complete default configuration generated by `worsier --init`:

```jsonc
{
  "$schema": "./node_modules/worsier/configuration_schema.json",
  "lineWidth": 120,
  "verifyAst": true,
  "rules": {
    "bracketSpacing": {
      "curly": "always",
      "square": "never"
    },
    "classMemberSpacing": "smart",
    "commentSpacing": true,
    "importLayout": true,
    "exportLayout": true,
    "interfaceLayout": 0,
    "typeLiteralLayout": 0,
    "unionLayout": "auto",
    "objectPropertySpacing": true,
    "quoteStyle": "single",
    "statementSpacing": {
      "controlFlowStatements": "separate",
      "imports": "separate",
      "multilineCallStatements": "separate",
      "returnStatements": "separate",
      "singleLineCallStatements": {
        "betweenCalls": "compact",
        "withOtherStatements": "separate"
      },
      "typeAliases": "separate",
      "variableDeclarations": "separate"
    },
    "semicolons": {
      "statements": "asNeeded",
      "classMembers": "asNeeded",
      "typeMembers": {
        "singleLine": "asNeeded",
        "multiline": "always"
      }
    },
    "trailingCommas": "never"
  },
  "ignorePatterns": []
}
```

`ignorePatterns` accepts glob patterns. Unknown keys and invalid values are configuration errors.

## Formatting rules

| Rule | Default | What it controls |
| --- | --- | --- |
| `rules.bracketSpacing` | `{ "curly": "always", "square": "never" }` | Spaces inside object-style braces and array-style brackets |
| `rules.classMemberSpacing` | `"smart"` | Blank lines between class members and overload groups |
| `rules.commentSpacing` | `true` | Blank lines around standalone comment groups |
| `rules.importLayout` | `true` | Layout inside static imports |
| `rules.exportLayout` | `true` | Layout inside nonempty named exports and re-exports |
| `rules.interfaceLayout` | `0` | TypeScript interface expansion threshold |
| `rules.typeLiteralLayout` | `0` | Object type expansion threshold inside TypeScript type and interface declarations |
| `rules.unionLayout` | `"auto"` | Union layout inside TypeScript type and interface declarations |
| `rules.objectPropertySpacing` | `true` | Layout and spacing between object-literal properties |
| `rules.quoteStyle` | `"single"` | Delimiters and quote escapes in JavaScript and TypeScript strings |
| `rules.statementSpacing.controlFlowStatements` | `"separate"` | Boundaries around direct control-flow statements |
| `rules.statementSpacing.imports` | `"separate"` | Boundaries around static imports |
| `rules.statementSpacing.multilineCallStatements` | `"separate"` | Boundaries around direct multiline call statements |
| `rules.statementSpacing.returnStatements` | `"separate"` | Boundaries around direct return statements |
| `rules.statementSpacing.singleLineCallStatements` | `{ "betweenCalls": "compact", "withOtherStatements": "separate" }` | Boundaries between direct single-line call statements and their siblings |
| `rules.statementSpacing.typeAliases` | `"separate"` | Boundaries around direct type aliases |
| `rules.statementSpacing.variableDeclarations` | `"separate"` | Boundaries around direct runtime variables |
| `rules.semicolons.statements` | `"asNeeded"` | Runtime and TypeScript statement endings |
| `rules.semicolons.classMembers` | `"asNeeded"` | Class field and declaration endings |
| `rules.semicolons.typeMembers` | `{ "singleLine": "asNeeded", "multiline": "always" }` | Interface and object-type member endings |
| `rules.trailingCommas` | `"never"` | Optional trailing commas in supported lists |

### Bracket spacing

`bracketSpacing.curly` and `bracketSpacing.square` each accept `"always"`, `"never"`, or `"off"`. The defaults add one space inside nonempty object-style braces and remove spaces inside array-style brackets:

```ts
let { taskId } = receipt
const items = [one, two]
```

Curly spacing covers object literals, object destructuring, named static imports and exports, import attributes, and TypeScript object types and interfaces. Square spacing covers array literals, array destructuring, and TypeScript tuples. Code blocks, JSX expression braces, indexed access, and computed keys are outside this rule. Empty `{}` and `[]` have no inner spaces. Each mode changes only same-line spaces and tabs next to a delimiter; it preserves line breaks, indentation, and comment text. `"off"` disables this rule for that delimiter; other enabled rules, such as `importLayout`, can still change its layout.

### Comments

`commentSpacing` separates a standalone comment group from preceding code with a blank line when the group is immediately followed by code on the next line. Existing blank lines above the group are preserved. Adjacent `//`, `/* */`, and JSDoc comments form one group unless a blank line separates them; the group stays adjacent to its target code.

```ts
function run() {
  // First action
  woof()

  // Second action
  bark()
}
```

The rule applies throughout supported scripts, including statements, class and type members, objects, arrays, arguments, parameters, and import/export specifiers. It does not add padding before the first element of a file, body, or list, including unbraced and concise arrow bodies, switch-case consequents, and parenthesized first generic arguments. Comments sharing a line with code, including `/* comment */ call()` and trailing comments, are outside this rule. Import layout preserves the same-line connection between a multiline block comment and the following code, so it does not become a standalone group on a later formatting pass.

A group separated from following code by a blank line is detached. Its original blank-line counts on both sides are preserved, as are the gaps around comments before a closing delimiter or end of file. Generic closing brackets are distinguished from relational operators such as `>`. These comment gaps take precedence over other spacing and layout rules, including `"compact"`. Comment text and directive adjacency are preserved.

Set `commentSpacing` to `false` to retain the previous behavior: other enabled rules determine the gap before a leading comment group and normalize a detached gap after it to one blank line when rewriting that boundary. The comment rule also works when every other rule is disabled.

### Imports

`importLayout` formats only static imports. Named specifiers stay on one line while the complete import fits `lineWidth`; otherwise each specifier is placed on its own line. Specifier order, aliases, attributes, and comments are preserved. Default-only, namespace, side-effect, and dynamic imports are not expanded. The final module quotes and escapes are controlled independently by `quoteStyle` and count toward `lineWidth`.

```ts
import {
  type Config,
  format
} from 'worsier'
```

Set `importLayout` to `false` to preserve the existing import layout. Quote, trailing-comma, and statement-semicolon rules remain independent; set `rules.quoteStyle`, `rules.trailingCommas`, and `rules.semicolons.statements` to `"off"` as well when the complete import text must remain unchanged.

### Exports

`exportLayout` formats nonempty named local exports and re-exports, including `export type`, inline `type` specifiers, aliases, and string-named specifiers. The default is `true`: the complete export stays on one line when it fits `lineWidth`; otherwise each specifier gets its own line with two-space indentation. An existing multiline list can collapse when it fits and comments allow it.

```ts
export {
  format,
  loadConfig,
  type FormatConfig
} from './formatter'
```

Width includes the final indentation, quotes and escapes, brace spaces, trailing commas, attributes, and statement ending. The width limit is inclusive, as it is for imports. Specifier order, aliases, sources, attributes, and comment text are preserved. Line comments and protected comment gaps can keep a list multiline. An export with tokens on a line covered by `// @ts-ignore` or `// @ts-expect-error`, including their block-comment forms, keeps its layout so the directive still covers the same code.

Empty exports, wildcard and namespace re-exports, default exports, and exported declarations are outside this rule. Worsier does not sort, split, merge, or reorder exports.

Set `exportLayout` to `false` to preserve the existing export layout, including when upgrading from a release without this rule. Other enabled rules can still change quotes, brace spaces, commas, semicolons, and comment gaps. Disabling export layout does not disable import layout, and the rule also works when all other rules are disabled.

### Quotes

`quoteStyle` accepts `"single"`, `"double"`, or `"off"`. Its default `"single"` mode applies the selected delimiter strictly, escaping that delimiter and removing an unnecessary escape from the opposite quote:

```ts
const message = 'don\'t say "later"'
```

The rule covers JavaScript and TypeScript string expressions, quoted property names, string literal types, module sources and string-named import/export specifiers, import attributes, and directives. Template delimiters and text are preserved, while ordinary strings inside `${...}` are formatted. JSX string attributes are preserved; JavaScript strings inside JSX expression containers are formatted. Vue templates, tags, attributes, styles, and other non-script content remain unchanged.

Set `quoteStyle` to `"off"` to preserve existing string delimiters and escapes. Because the default is `"single"`, upgrading without an explicit setting changes double-quoted strings to single-quoted strings.

### Interfaces

`interfaceLayout` is either `"off"` or a member threshold from `0` through `4294967295`. An interface expands only when its direct member count is greater than the threshold, so the default `0` expands every nonempty interface.

```ts
interface Example {
  value: string;
  run(): void;
}
```

Member text, order, comments, and nested layout are preserved. Separators remain controlled independently by `rules.semicolons.typeMembers`. Members covered by a preceding `// @ts-ignore` or `// @ts-expect-error` remain on the same physical line so formatting does not change the directive's scope. Object type literals are controlled independently by `typeLiteralLayout`.

### Object types

`typeLiteralLayout` is either `"off"` or a member threshold from `0` through `4294967295`. An object type inside a TypeScript `type` or `interface` declaration expands only when its direct member count is greater than the threshold. The default `0` expands every nonempty object type in these declarations; `1` leaves single-member types inline. The threshold does not depend on `lineWidth` and never collapses an existing multiline type.

```ts
type User = {
  id: string;
  name: string;
}
```

The rule covers object types throughout `type` and `interface` declarations, including nested properties, generic arguments, and function signatures within these declarations. Exported, ambient, namespace, and function-local declarations are included, as are declarations in TypeScript Vue scripts. Properties, methods, index signatures, call signatures, and construct signatures each count as one member. Every nested object type uses its own direct member count, even when its parent is below the threshold. Interface boundaries remain controlled by `interfaceLayout`; mapped-type boundaries are outside this rule, while object types nested within them are still formatted.

Outside these declarations, variable and class-field annotations, function parameters and return types, generic arguments in calls, `as`, and `satisfies` keep their object type layout through this rule. Other enabled rules can still change their spaces, comments, quotes, and semicolons.

Member text, order, comments, existing member indentation, and existing closing-brace indentation are preserved. When union layout moves an object variant, its object type bodies keep their relative indentation at the new position. New member lines use neighboring member indentation when available, otherwise two spaces beyond the containing line or member. For a fully inline type, the closing brace aligns with its containing line or member. Nested layout changes affect surrounding statement spacing in the same formatting run. `semicolons.typeMembers` controls separators using each container's final layout; commas between type members are preserved.

Members covered by a preceding `@ts-ignore` or `@ts-expect-error` stay on the same physical line, including members sharing a line with the end of a multiline type. Both line comments and block comments such as `/* @ts-expect-error */` are supported; a block directive must appear on the comment's final line, as required by TypeScript. An object type beginning on a directive's target line is not expanded, including when the directive precedes the whole alias. Protected boundaries between a type's closing brace and the next statement are also preserved. Existing `commentSpacing` protections take precedence over boundary normalization.

Set `typeLiteralLayout` to `"off"` to preserve object type boundaries through this rule. Other enabled rules can still change spaces, comments, quotes, and semicolons inside the type. Upgrading from a version with broader type layout leaves inline annotations outside declarations unchanged through this rule; it does not undo their existing layout.

### Union types

`unionLayout` accepts `"auto"`, `"always"`, or `"off"` and applies inside TypeScript `type` and `interface` declarations. For unions that are not entirely made of object type literals, the default `"auto"` keeps a union on one line when its complete rendered line fits `lineWidth`, including indentation, surrounding syntax, quotes, and separators. The width limit is inclusive. An existing multiline union can collapse when its variants and comments allow it; a variant that remains multiline keeps the union multiline.

```ts
type Identifier = string | number
```

When such a union is too long, or with `"always"` for any union, each variant of a union with two or more variants starts on its own line with a leading `|` and two additional spaces relative to its containing line's final indentation. Existing member indentation is respected even when the parent layout rule is off:

```ts
type Identifier =
  | string
  | number
```

In `"auto"`, a union whose variants are all object type literals keeps its first object after `=` or `:` and joins the remaining variants with ` | `, even when the objects are multiline or the line exceeds `lineWidth`:

```ts
type PackingListEntryCreateBody = {
  customName: string;
} | {
  inventoryId: string;
}
```

Object body expansion remains controlled by `typeLiteralLayout`, so disabling it or raising its threshold can leave these unions inline even beyond `lineWidth`. Required grouping parentheses are preserved. A mixed union such as `{ value: string } | null`, or a union of named types, uses the ordinary width-based layout. `"always"` keeps leading pipes for object unions as well. Boundaries containing comments retain their existing layout. Moving a variant shifts its existing relative indentation even when `typeLiteralLayout` is off or its threshold prevents expansion. This shift changes only indentation outside tokens and comment text; it preserves existing line breaks and the position of variants whose commented boundaries stay on separate lines.

The rule covers nested types and signatures within type and interface declarations, including exported, ambient, namespace, function-local, and Vue script declarations. Unions in variable and class-field annotations, function parameters and return types, generic calls, `as`, and `satisfies` outside these declarations keep their layout through this rule, including existing multiline unions. Other enabled rules remain independent.

Variant order, content, grouping, required parentheses, comment connections, and protected comment gaps are preserved. Unions with tokens on a line covered by `@ts-ignore` or `@ts-expect-error`, including block-comment directives, keep their layout even when `commentSpacing` is disabled. Nested layout changes affect surrounding declaration and statement spacing in the same formatting run.

Set `unionLayout` to `"off"` to preserve union layout through this rule. Upgrading from a version with broader union layout leaves annotations outside declarations unchanged through this rule; it does not restore their earlier layout. Worsier does not sort or deduplicate variants or format intersection boundaries through this rule.

### Object properties

`objectPropertySpacing` formats object literals with at least two direct elements as multiline objects. Two single-line elements are separated by one line break; if either neighboring element is multiline in the final output, they are separated by exactly one blank line. Newly expanded objects use two-space indentation, while existing multiline indentation and the source newline style are preserved.

```ts
const options = {
  compact: true,

  nested: {
    first: 1,
    second: 2
  },

  ...defaults
}
```

The rule covers ordinary, shorthand, computed, method, getter, setter, and spread elements. Nested object and statement layouts cascade in the same formatting run, so a property that becomes multiline immediately affects both neighboring boundaries. Leading comments stay with the following element, trailing comments stay with the preceding element, and line-scoped TypeScript directives remain adjacent to their target. Empty and single-element objects are not expanded. Object patterns, TypeScript object types and interfaces, classes, and import/export specifiers are outside this rule.

Set `objectPropertySpacing` to `false` to preserve object braces and property boundaries. Other enabled rules can still format content inside an object literal.

### Class members

`classMemberSpacing` accepts `"smart"`, `"separate"`, `"compact"`, or `"off"`. The default `"smart"` keeps adjacent single-line fields together and adds one blank line when either neighbor is a method-like member or a multiline field:

```ts
class Counter {
  value = 0
  limit = 10

  increment() { this.value += 1 }

  reset() { this.value = 0 }
}
```

`"separate"` uses one blank line between every logical member group; `"compact"` uses one line break. Overload signatures and their implementation form one group, with one line break between its members in all enabled modes. Signature-only overload families also stay together. Constructors, methods, getters, setters, auto-accessor properties, and static blocks use method-like boundaries. Ordinary fields and TypeScript index signatures use field boundaries. Fields are classified by their final layout, including decorators and changes made by other enabled rules, in the same formatting run.

The rule covers class declarations and expressions, nested classes, and supported static, private, abstract, and declared members. Inline lists with two or more members expand into a block, including overload groups. Existing indentation is preserved; new member lines use neighboring member indentation, otherwise two spaces beyond the containing line or member. Existing gaps before the first member and after the last member are preserved; newly expanded edges use one line break. Empty and single-member classes are not expanded by this rule. Member contents, order, decorators, modifiers, and computed keys are preserved, and `lineWidth` does not affect the rule.

Comments stay with their members. Existing `commentSpacing` protections and line-scoped TypeScript directive targets take precedence over every mode, including `"compact"`. Class-member semicolons and automatic semicolon insertion guards remain controlled by `semicolons.classMembers`.

Set `classMemberSpacing` to `"off"` to preserve member boundaries through this rule. Other enabled rules still format content inside classes. Upgrading without an explicit setting enables `"smart"` and can change class layout.

### Statement spacing

Most spacing settings accept one of three modes:

| Mode | Result |
| --- | --- |
| `"separate"` | Add category-specific blank lines; direct control-flow, multiline call, and `return` statements are also separated from same-category siblings |
| `"compact"` | Use exactly one line break |
| `"off"` | Do not impose a boundary |

When two configured statement categories meet, the stricter boundary wins; enabled `commentSpacing` takes precedence for comment gaps. Spacing can also unfold an inline statement list, using two-space indentation.

`singleLineCallStatements` accepts either a mode shorthand or an object with independent `betweenCalls` and `withOtherStatements` modes. A shorthand applies the same mode to both boundaries. Missing object fields keep their documented defaults, so `{ "betweenCalls": "off" }` preserves existing gaps between consecutive single-line calls while continuing to separate them from other statements. An `"off"` boundary imposes no requirement of its own; another configured category can still win at the same boundary.

Control-flow spacing applies to direct `if`, `switch`, `for`, `for...in`, `for...of` (including `for await...of`), `while`, `do...while`, and `try` statements at every nested statement-list level. Braced and unbraced bodies are treated alike, while `else`, `catch`, and `finally` stay inside their owning statements. Labelled wrappers are not direct control-flow statements. Call spacing applies only to direct expression statements whose outer expression, after parentheses, TypeScript wrappers, optional chaining, and any `await`, is a `CallExpression`; ordinary, method, optional, generic, and `super` calls are covered. A call is single-line when its final call span has no physical line break and multiline otherwise, including when a nested layout rule introduces the break in the same formatting run. The call rules do not wrap calls, do not add padding against block or file edges, and exclude `new`, dynamic imports, tagged templates, `void`, `yield`, assignments, variable initializers, and calls inside `return` or `throw`. Return-statement spacing applies to direct `return` statements in the same statement list. In `"separate"` mode, every adjacent boundary around direct control-flow, multiline call, and `return` statements gets one blank line, including a boundary between two statements from the same category; a lone statement in one of those categories does not unfold its parent list. Statements covered by a preceding `// @ts-ignore` or `// @ts-expect-error` remain attached so spacing does not change the directive's scope. Type-alias spacing applies to direct, unexported `type` declarations. Variable spacing applies to direct runtime `const`, `let`, and `var` declarations. Exported or ambient declarations and variables in `for` headers are left outside those rules.

```ts
isHolding.value = false

emit('complete')
holdTimer.stop()

emit({
  body: formData
})

finish()
```

```ts
function process(items: Item[]) {
  const results = []

  for (const item of items) {
    if (item.valid) results.push(item)
  }

  if (results.length === 0) return null

  return results
}
```

### Semicolons

Each semicolon group accepts `"always"`, `"asNeeded"`, or `"off"`. `"asNeeded"` removes optional semicolons and inserts a leading guard when the next statement or computed class member could otherwise be joined by automatic semicolon insertion:

```ts
const values = load()
;[first, second].forEach(use)
```

Required semicolons, `for` header separators, standalone empty statements, and commas between TypeScript type members are preserved. `"off"` leaves the selected group unchanged.

`typeMembers` also accepts an object with independent `singleLine` and `multiline` modes. Its default uses `"asNeeded"` for single-line type containers and `"always"` for multiline containers, so `{ first: number; second: string; }` becomes `{ first: number; second: string }` while multiline interfaces, object types, and mapped types keep their trailing semicolons. Each container uses its own final physical layout after other rules run. A string value remains shorthand for applying the same mode to both layouts. The semicolon ending a type alias remains controlled by `statements`; `typeMembers` controls only members inside the type.

### Trailing commas

`trailingCommas` accepts `"always"`, `"never"`, or `"off"`:

- `"always"` adds a comma to eligible multiline lists and removes it from single-line lists.
- `"never"` removes optional trailing commas.
- `"off"` preserves them.

The rule covers object and array literals, destructuring, named static imports and exports, parameters, arguments, tuples, enums, and type parameters. It preserves commas that are required by syntax or semantics, including sparse-array elisions, and never adds a comma after a rest item. Dynamic `import()` arguments and TypeScript type arguments are not changed.

## Vue SFC support

For `.vue` files, Worsier formats inline `<script>` and `<script setup>` blocks. Scripts without `lang` and scripts using `lang="js"`, `lang="jsx"`, `lang="ts"`, or `lang="tsx"` use the corresponding JavaScript or TypeScript parser.

Generated lines preserve the script's existing top-level indentation, and import and export wrapping count that indentation toward `lineWidth`.

Templates, styles, custom blocks, tags, and attributes are preserved byte-for-byte. Scripts with a `src` attribute and scripts using any other `lang` value or a valueless `lang` attribute are also preserved; Worsier never reads an external script referenced by `src`.

## Programmatic API

```js
import { format } from 'worsier'

const output = await format(
  'example.ts',
  "import{answer,type Value}from'pkg'",
  { rules: { trailingCommas: 'always' } }
)
```

`format(fileName, sourceText, config?)` returns a promise with the formatted source. The optional `FormatConfig` argument uses the same defaults as the CLI, but the API does not discover configuration files.

## Guarantees and scope

- Worsier preserves source outside the regions controlled by enabled rules, including the independently configured import, export, interface, object-type, union, and class-member layouts.
- Rewritten text keeps the source's LF or CRLF line endings. UTF-8 BOM and final-newline presence are preserved.
- `verifyAst: true` reparses each rewritten script and rejects changes that do not match its input Oxc AST.
- Formatting is idempotent: formatting an already formatted file produces no further changes.
- Set every rule to `"off"` or `false` to make formatting return the source unchanged.

## Development

Repository scripts, npm package tests, and benchmark tooling use native ESM TypeScript (`.mts`) executed directly by Node.js without a loader or transpilation step. Run `vp run check:types` for strict no-emit type checking; the complete `vp run check` includes that check alongside the Rust, npm, native-package, and benchmark suites.

Local development pins Node.js 24 LTS, Rust 1.98.1, and pnpm 12.6.0. Linux CI checks use Ubuntu 26.04; release binaries for Linux still build on Ubuntu 24.04 to preserve their glibc compatibility baseline.

On macOS, CLI tests compare ACL entries by UUID before and after file updates without resolving UUIDs to account names.

## Performance benchmarks

Import and export indentation lookups share a line index across layout passes, so declarations on one physical line do not repeatedly scan the preceding source text.

Benchmarks are manual snapshots, not release gates. The comparative suite measures Worsier, Prettier, and Oxfmt on the same small TypeScript input, TypeScript's `parser.ts`, and a pinned Outline source corpus. Run `vp run benchmark` for an ignored draft or `vp run benchmark:update` from a clean committed worktree to replace the published snapshot. See the [benchmark guide](benchmark/README.md) for the complete methodology.

## Releases

Release Please treats the complete repository as one releasable component, so conventional commits that change the Rust formatter, CLI, documentation, or npm package can all produce a release pull request. The private root `package.json` version is release metadata and must stay synchronized with the publishable package, Cargo workspace, lockfiles, and platform packages; `vp run check:versions` verifies that contract.

## Alternatives

[Prettier](https://prettier.io/docs/) is a mature opinionated formatter that prints the complete source. [Oxfmt](https://oxc.rs/docs/guide/usage/formatter.html) is a fast, Prettier-compatible formatter with broader language and formatting coverage. Worsier instead focuses on independent source-rewrite rules and preserving text outside those rules.
